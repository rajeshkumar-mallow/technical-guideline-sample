# Internationalization (Frontend)

**Read this first.** Retrofitting i18n into an app built with hardcoded strings and layout that assumes left-to-right, short English text is a rewrite, not a feature. Bake the structure in even for a project that ships one locale today.

**Applies to:** any frontend codebase. Next.js App Router-specific routing/middleware live in [`next/i18n.md`](next/i18n.md).

---

## Mandatory

### Never hardcode user-facing strings
- Every user-facing string goes through a translation function/component (`t("key")`), even in a single-locale project — the cost of doing this from day one is far lower than a retrofit.
- Keys are namespaced by feature/page (`checkout.submitButton`), not by raw English text (`"Submit Order"`) — the raw string is a translatable value, not a stable identifier.

### Locale/translation file structure
- One JSON (or equivalent) file per locale per namespace: `locales/en/checkout.json`, `locales/fr/checkout.json` — keeps diffs reviewable and avoids one giant monolithic translation file.
- Keep translation files **flat or shallow** (2 levels max) — deep nesting makes keys hard to grep and translation-management tools harder to integrate.

```json
// locales/en/checkout.json
{
  "submitButton": "Place order",
  "itemCount": "{count, plural, one {# item} other {# items}}"
}
```

### Pluralization
- Use ICU MessageFormat (via `Intl.PluralRules` or a library like `format-message`/`i18next` with ICU support) for plural rules — **never** string-concatenate a count with a hardcoded `"item" + (n !== 1 ? "s" : "")`. Many languages have more than two plural forms (Arabic has six).

```ts
const pluralRules = new Intl.PluralRules(locale);
pluralRules.select(itemCount); // "one" | "other" | "few" | "many" | ...
```

### RTL support
- Use **logical CSS properties** (`margin-inline-start`, `padding-inline-end`, `inset-inline-start`) instead of physical ones (`margin-left`, `padding-right`) so layout flips automatically under `dir="rtl"` — don't hand-maintain a mirrored stylesheet.
- Set `dir` on `<html>` based on the active locale's directionality; test at least one RTL locale (Arabic or Hebrew) in the primary user flow before calling i18n "done," even if RTL isn't launched yet.

### Date, number, and currency formatting
- Use the native `Intl` APIs — never hand-format dates/numbers/currency with string manipulation, which breaks silently across locales.

```ts
new Intl.DateTimeFormat(locale, { dateStyle: "medium" }).format(date);
new Intl.NumberFormat(locale, { style: "currency", currency: "USD" }).format(amount);
```

- Store/transmit dates in UTC/ISO 8601; format to the user's locale **only at render time** (ties to the Rails guideline's own UTC-storage rule for consistency across the stack).

## Recommended (opt-in)

- A **translation management platform** (Lokalise, Crowdin, etc.) once the string count or number of locales makes spreadsheet/manual handoff unworkable.
- **Pseudo-localization** in CI/dev builds (e.g. `[ŘṦṦŠŠŠŠ]`) to catch untranslated or layout-breaking strings before a real translator ever sees them.
- Locale-aware **collation** (`Intl.Collator`) for sorting user-facing lists (e.g. names) rather than default string sort, which is incorrect for accented characters in many locales.

## Anti-Patterns (do not ship)

- Hardcoded English strings inline in components "to add i18n later."
- Manual plural logic (`count === 1 ? "item" : "items"`) instead of ICU/`Intl.PluralRules`.
- Physical CSS properties (`margin-left`) in components expected to support RTL.
- Hand-formatted date strings (`"${month}/${day}/${year}"`) instead of `Intl.DateTimeFormat`.
- Translation keys that are the English sentence itself (breaks when the English copy changes for wording, not translation, reasons).

## Quick Reference

```
✓ Every string through t()/translation component, even single-locale
✓ Namespaced, flat translation files per locale
✓ ICU plural rules via Intl.PluralRules — never manual count-based branching
✓ Logical CSS properties for RTL-safe layout; dir on <html>
✓ Intl.DateTimeFormat / Intl.NumberFormat for all locale-formatted output
✗ Hardcoded strings, manual pluralization, physical CSS properties, hand-formatted dates
```
