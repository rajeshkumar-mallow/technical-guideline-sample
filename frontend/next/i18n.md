# Internationalization (React/Next)

**Read this first.** Locale-aware routing has to be decided at the App Router's structural level (which URLs exist, how locale is detected) before any translation library choice matters. General i18n content conventions (pluralization, date/number formatting, RTL) live in [frontend/i18n.md](../i18n.md); this file covers the Next-specific routing and rendering layer.

**Applies to:** any React/Next project supporting more than one locale.

---

## Mandatory

### `[locale]` segment routing
Locale lives in the URL as a top-level dynamic segment, not a query param or cookie-only scheme — this keeps locale-specific pages crawlable, shareable, and cacheable independently.

```
app/
  [locale]/
    layout.tsx       # validates locale, provides translations to the tree
    page.tsx
    dashboard/
      page.tsx
```

```tsx
// app/[locale]/layout.tsx
export function generateStaticParams() {
  return locales.map((locale) => ({ locale }));
}

export default async function LocaleLayout({ children, params }: { children: React.ReactNode; params: Promise<{ locale: string }> }) {
  const { locale } = await params;
  if (!locales.includes(locale)) notFound();
  return (
    <html lang={locale}>
      <body>{children}</body>
    </html>
  );
}
```

`<html lang={locale}>` is mandatory for every locale — it's a WCAG requirement (see [Accessibility](../accessibility.md)), not just SEO nicety.

### Middleware-based locale detection
Detect the visitor's preferred locale (via `Accept-Language`, then a locale cookie for repeat visits) and redirect to the localized URL in `middleware.ts` — do this once, centrally, rather than per-page.

```ts
// middleware.ts
export function middleware(request: NextRequest) {
  const pathname = request.nextUrl.pathname;
  const hasLocale = locales.some((l) => pathname.startsWith(`/${l}`));
  if (hasLocale) return;

  const locale = detectLocale(request); // Accept-Language header, then cookie fallback
  return NextResponse.redirect(new URL(`/${locale}${pathname}`, request.url));
}
```

Never silently render one locale's content at a URL that implies another (e.g. `/en/dashboard` must never render French copy) — locale in the URL is a contract.

### Library: `next-intl`
Default to **`next-intl`** for translation loading, formatting, and routing helpers, rather than hand-rolling a translation dictionary loader. Rationale: first-class App Router + Server Component support (translations load server-side, no client bundle cost for message catalogs), typed message keys, and built-in `Link`/`redirect`/`usePathname` helpers that stay locale-aware automatically. Document any deviation (e.g. an existing `react-i18next` investment) as an ADR.

```tsx
import { useTranslations } from "next-intl";

export default function WelcomeBanner() {
  const t = useTranslations("Home");
  return <h1>{t("welcome", { name: user.name })}</h1>;
}
```

### Static vs. dynamic locale rendering
- Prefer **static rendering per locale** (`generateStaticParams` over the locale list) for content that doesn't depend on the individual user — this pre-renders every locale variant at build time with no per-request translation-loading cost.
- Fall back to **dynamic rendering** only for locale-dependent pages that are also user-specific (e.g. a localized dashboard) — accept the per-request cost there since the page is already dynamic for other reasons.
- Never make an entire app dynamic purely because it's localized — locale alone is not a reason to opt out of static rendering.

## Recommended (opt-in)

- RTL locales (Arabic, Hebrew) get a `dir="rtl"` attribute driven off the same locale value used for `lang`, and a QA pass specifically for mirrored layouts — ties to [Responsive Design](../responsive-design.md).
- Split translation message catalogs per route/namespace (`Home.json`, `Dashboard.json`) rather than one monolithic file, so `next-intl` only loads what a given route needs server-side.

---

## Anti-Patterns (do not ship)

- Locale stored only in a cookie/client state with no URL segment — breaks shareable links and crawling.
- Missing or incorrect `<html lang>` per locale.
- Hardcoded strings in components outside the translation catalog "because it's just one label" — these accumulate and are the hardest to find later.
- Making an otherwise-static page dynamic solely because it needs translations.
- A locale mismatch between the URL and the rendered content (URL says `/fr/`, content renders in English due to a fallback bug).

## Quick Reference

```
✓ Locale as a [locale] URL segment, validated in the layout
✓ Middleware detects + redirects to the right locale, once, centrally
✓ next-intl for translation loading and locale-aware navigation helpers
✓ <html lang> set correctly per locale; dir="rtl" for RTL locales
✓ Static rendering per locale via generateStaticParams where content isn't user-specific
✗ No locale-only-in-cookie schemes, no hardcoded strings outside the catalog
✗ No page forced dynamic purely because it's translated
```
